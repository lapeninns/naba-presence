# R2-W6b: Supabase Data API exposure (W6-01 / W6-02 follow-up)

- **Scope:** read-only static analysis of the repository at the working-tree state on 2026-10-14. I touched no database, no Supabase/Vercel API and no secrets. I didn't attempt the exploit. Docker isn't running, so there was no local stack.
- **Method:** a throwaway parser (`/tmp/r2w6b/scan.py`, not committed) replayed all 131 files in `supabase/migrations` in order. It tracked `create`/`drop` of functions, tables, policies, views and sequences, plus RLS enable/force. I then checked each result by hand against the SQL. The parser can't see dynamic `execute format(...)` statements, so I reconciled the RLS loop at `0001_initial.sql:506-529` manually.
- **Inputs from the coordinator, taken as confirmed:**
  - No migration revokes from `anon`/`authenticated`.
  - `provision_local_bootstrap` has only `revoke … from public`.
  - `organisation_job_route_read` is `using (true)` with no `TO`.
  - `config.toml` exposes `public` and `graphql_public`.

## Verdict

- **The code-level chain is CONFIRMED.** Every SECURITY DEFINER function, and every table without RLS, in `public` is reachable by `anon`/`authenticated` _if_ the hosted project carries Supabase's standard default ACLs. No migration removes those grants.
- **Production state is still PLAUSIBLE, about 80% likely.** It needs the read-only SQL in section 3.
- **Practical exploitability today is lower than W6-01 implied.** An attacker needs two values that this app doesn't publish, although neither is a secret by design:
  - **The project URL/ref.** CSP `connect-src` reveals it only when `MEDIA_ASSET_STORAGE=supabase`. That name is absent from the production receipt's `configNames`. The auth email templates link to the app's own domain (`{{ .RedirectTo }}` + `{{ .TokenHash }}`), not to `*.supabase.co`.
  - **The publishable (or legacy anon) key.** It's server-only: `lib/server/password-auth.ts:95-115`. There's no `NEXT_PUBLIC_*` variable, no supabase-js, and no `apikey` usage in `app/` or `components/`.

  I'm correcting W6-01 on this: its "easy discovery" claim holds only for deployments that use Supabase Storage.
- **Impact if reached is CRITICAL.** It's worse than W6-01 stated:
  - two more account-takeover primitives (`provision_authenticated_user`, `provision_google_user`);
  - anon can execute the operator-only functions (`recover_user_mfa`, `revoke_support_sessions`);
  - `schema_migration` is writable, which lets an attacker silently skip a future migration or brick boot.
- **Priority stays P0.** The only thing in the way is Supabase's assurance that these keys are safe to expose, which is the assumption the tenancy model breaks.

## 2. Blast radius (scripted over all 131 migrations)

I assume the anon/authenticated grants exist. `anon` has no way to set `app.organisation_id` / `app.user_id` / `app.session_token_hash`:

- PostgREST sets only `request.*` GUCs and the role.
- `set_config` isn't in an exposed schema.
- Each request is its own transaction.

So **every policy keyed on those GUCs evaluates to NULL, which means deny, for anon.** Tenant tables with the standard `tenant_isolation` policy are safe even when granted. The exposure is SECURITY DEFINER functions (they run as `postgres`, which has BYPASSRLS), tables without RLS, and `true` policies.

### 2a. SECURITY DEFINER functions in `public` (50 live; ranked by what `anon` could do)

All 50 have `set search_path = public`. Each was created by `postgres` and revoked only from PUBLIC (or also from `naba_app_runtime`). That leaves the default-ACL grant to `anon`/`authenticated` intact.

There are also two live SD functions the parser had marked dropped because they were re-created. I verified both by hand:

- `claim_due_jobs(integer, integer, integer, text[])` (`0092:71`, SD at `:86`)
- `provision_google_user(text, text, text, boolean)` (`0008:163-237`)

Five SD functions return `trigger`. PostgREST doesn't expose those and they can't be called directly, so I list them but they're not reachable: `assert_organisation_retains_owner`, `prune_location_member_on_member_delete`, `location_link_enforce_limit`, `organisation_billing_plan_matches`, `organisation_seed_pilot_billing`.

### 2c. Views and sequences

- **Views:** none. No `create [materialized] view` survives in `supabase/migrations`, so there's no `security_invoker` question.
- **Sequences:** one identity sequence (`0090_pause_controls.sql`). The default ACL grants anon USAGE/SELECT/UPDATE, but PostgREST can't call `nextval`/`setval` (they're in `pg_catalog`). Negligible.
- **pg_graphql (`graphql_public`):** reachable only if grants exist, and it mirrors the PostgREST surface. The same fix covers it.
