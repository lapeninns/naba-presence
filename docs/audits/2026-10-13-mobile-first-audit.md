## foundations

The foundations are well engineered for a desktop operator's console and only patched for phones. The best parts are worth keeping as they are. The 4-layer token model, semantic role names, contrast gate (178/178 pairs pass, measured from the shipping CSS in both themes) and tokenised motion with a global reduced-motion collapse are all sound. Literal-colour discipline in TSX is excellent (0 oklch, 0 rgb).

The mobile-first gaps are structural:
(1) No `viewport` export. There is no viewport-fit=cover, themeColor or interactiveWidget, so every env(safe-area-inset-*) in the codebase (8 sites) resolves to 0 on iOS, and the browser chrome ignores dark mode.
(2) The type scale is desktop-dense. 12px and 13px roles make up 1,051 of the roughly 1,240 role uses, and body is 14px. 51 sizes sit below 12px, including badges, stacked table labels and the eyebrow. Only fields jump to 16px on touch, which inverts hierarchy (field value bigger than its label).
(3) Touch sizing is an opt-in `(pointer: coarse)` override: 36px by default, plus 57 ad-hoc `pointer-coarse:` patches with values from 32px to 44px. No e2e project emulates touch.
(4) Focus is a box-shadow with outline:none, so it disappears in forced-colors mode. Four different focus mechanisms are in use.
(5) There are no breakpoint, container, z-index or spacing tokens. The 640/768/1180 viewport and 620px height thresholds, plus 13 arbitrary container widths, are hard-coded.
(6) The JS layout hooks default to desktop on the server, so phones get desktop SSR HTML.

The token file also carries a lot of dead weight: material blur roles, unused keyframes and variants, all of lib/motion, density blocks and duplicate roles. Its dark theme bypasses the ramp layer it claims is canonical.

The contract test pins many of these decisions: exact 12/13/14px sizes, material blocks, the absence of a spacing scale, and PageFrame class strings. It will need to be rewritten alongside the rebuild.

### Retain

- Four-layer token architecture (ramps -> --np-* semantic roles -> component tokens -> shadcn aliases) and the semantic role vocabulary (surface/ink/line/fill/accent, status ink/tint/solid/on-solid): Sound separation; feature code reads roles via utilities (bg-surface 194, text-ink-muted 752, border-line 340 uses) and literal colours in TSX are effectively zero (0 oklch(, 0 rgb(, hex only for stored client colours in client-avatar.tsx:34-37). A rebuild can change values and add mobile tokens without touching feature code.
- Contrast gate: lib/design/contrast.ts + contrast-pairs.ts + tokens.ts, scripts/check-contrast.mjs, tests/design-tokens-contrast.test.ts, /design-system ContrastEvidence: Measures the shipping globals.css in both themes with one shared module, flags out-of-gamut colours and refuses color-mix (tokens.ts:109-115). - Dark theme designed for dark (not inverted), including the charcoal counter-surface flipping to near-white: All dark pairs pass; screenshots dark/*.png render coherently. Values should move onto a dark ramp but the intent is right.
- Motion tokens and reduced-motion handling (globals.css:433-443, 678-685, 780-793): 80 transitions use duration-(--np-*), only 1 literal duration (spinner.tsx:46), 0 transition-all; the global reduced-motion rule also collapses delays so nothing is stuck invisible.

- lib/hooks/use-dirty-guard.ts: Business-critical draft protection (sessionStorage stash on unmount/401, beforeunload, injected confirm, foreign-identity guard); UI-agnostic so it survives any redesign.
- useSyncExternalStore-based useMediaQuery/useHydrated: Correct hydration-safe mechanism; only the desktop-first defaults need changing (foundations-09).

### Business logic a rebuild must preserve

- Contrast gate semantics: every painted foreground/background pair is measured from the shipping CSS in both themes and fails CI (pnpm check:contrast, tests/design-tokens-contrast.test.ts); color-mix is refused for gated roles; out-of-gamut colours are flagged.
- Status is always a word plus a tone (lib/ui/status-tone.ts STATUS_TONES); a dot never stands alone; status words about Google ('Sent to Google', 'Live on Google') only from operation or verification evidence.
- Exactly one action region per screen 'reaches Google' (the charcoal ActionBar) and one primary accent action per surface. This is the visual approval/publish boundary.
- Disabled controls carry a visible reason and stay focusable (Button disabledReason/pending keep focus, aria-busy).
- useDirtyGuard behaviour: mirror dirty content to the sessionStorage draft stash, arm beforeunload while dirty, confirmDiscard via an injected dialog, markDiscarded after leave-guard consent, never stash or restore drafts across a different signed-in identity, and stash on unmount when the composer remounts across a breakpoint.
- breadcrumbTrail is URL-derived and mode-aware: business mode has no client crumbs or /clients trail; unfiled listings show 'Unfiled'.
- Form fields render at >=16px on touch devices so iOS never zooms on focus.
- prefers-reduced-motion collapses all animation and transition durations and delays.
- The skip link is the first tab stop and moves focus to the single <main id="main" tabIndex=-1>.
- The mobile navigation closes on any route change and when the viewport grows into the persistent-nav layout (no stranded focus trap or scroll lock).
- The inbox selection lives in URL state (?selected=) and the list/detail switch keys off DESKTOP_MEDIA_QUERY; list and controls stay mounted (hidden) so selection, aria-current and the dirty guard survive the swap.
- Theme: next-themes class strategy with defaultTheme 'system' and enableSystem; html suppressHydrationWarning.
- /design-system is notFound() unless DESIGN_SYSTEM_EVIDENCE_ENABLED, rendered force-dynamic, and calls no API.
- Tailwind scans only ./, ../components and ../lib (source(none) plus explicit @source) so saved HTML and test artifacts never leak classes.
- Every new type role must be registered in the tailwind-merge font-size group (lib/utils.ts) or cn() will drop colour or size classes.

## primitives-overlays-forms

The 21 primitives are a thin, mostly well-made skin over Base UI 1.9 (focus trap/return, Escape, scroll lock, touch-aware initial focus) plus cmdk. The form layer is the strongest part: Field wires id, aria-invalid and error-first aria-describedby without dangling IDREFs, Select/Combobox triggers take the label by aria-labelledby, and coarse pointers get 44px fields, 44px menu/select/command rows and 16px field text. Its weaknesses are adoption and one API trap: FieldError ignores its children, so danger-zone's destination error never renders, and the largest forms (bulk-compose, schedule-post-sheet, 30 hand-rolled fieldsets with 12 legend recipes) bypass Field entirely.

The overlay layer is desktop-first. Dialog has no phone presentation: it stays a centred card whose popup is the scroller, so the title and close X scroll away. Sheet's phone mode is a fixed 92dvh panel with a purely decorative grabber, no swipe or snap points, and no virtual-keyboard handling. Safe-area padding is inert because there is no viewport-fit=cover. Select, DropdownMenu, Combobox and Popover are floating popovers at every width with 13px rows. The listing switcher is a Combobox, so switching listing raises the keyboard. The client-switcher search input is overridden to 13px, so iOS zooms on focus. Only EditorFrame handles the keyboard. Base UI 1.9 already ships Drawer (swipeDirection, snapPoints, DrawerVirtualKeyboardProvider), Fieldset and ToggleGroup, all unused.

Touch targets are uneven. Switch and menu rows reach 44px. Checkbox and radio stay at 24px/18px, segmented items at 40px, and the segmented track clips with no scroll cue at 360px. One segmented visual carries three semantic models (tabs, aria-pressed, a hand-rolled radiogroup).

A mobile-first rebuild should keep Base UI and the Field contract. It should add one responsive overlay foundation (Drawer below sm, centred dialog or side panel above), touch presentations for pickers, keyboard and safe-area handling, a dirty-close guard built into the overlay, and touch-size tokens on every selection control.

## primitives-display-feedback

Repo root: /Users/amankumarshrestha/LapenInns Project/platform/naba-presence-redesign/integration. The display and feedback primitives are well written and well documented, with strong a11y intent: typed aria-label for icon buttons, mandatory table captions, spoken deltas, honest nulls, outcome wording that never claims "Live on Google" without evidence, and polite live regions. The weaknesses are coverage, overlap and mobile behaviour, not the code quality of each file.

(1) Mobile chrome is inert or hand-rolled. No viewport-fit=cover is set, so every env(safe-area-inset-*) in ActionBar, Toast, Sheet and the inbox footers resolves to 0. Bottom action bars are implemented at least six ways. ActionBar's own sticky API is bypassed by EditorFrame. Toasts sit at the TOP on phones, so Undo lands in the hardest thumb zone.

(3) Responsive tables are close to good. 20 of 21 feature tables opt into labelled rows. But selection breaks on phones: select-all is lost and the checkbox takes its own row. Card columns misalign, and first-cell labels are inconsistent.

(4) Heavy overlap and bypassing: 143 hand-rolled card class strings vs 19 Card importers. Three local KPI tiles. About 10 tone vocabularies for 5 states. Four loading/error/empty systems. Three segmented-control look-alikes. Two breadcrumb implementations.

(5) Dead code: SplitPane (0 importers) with react-resizable-panels; recharts charts and ChartCard (only ChartDataTable and ChartLegend are used); the Breadcrumbs component; Meter; AlertAction; unused Badge and Button variants.

A mobile-first rebuild should keep the behavioural contracts and collapse these into fewer primitives that are touch-sized and aware of safe areas.

- DataTable: caption mandatory; select-all affects only currently rendered rows, never filtered-out ones (data-table.tsx:94-102); checkbox clicks never trigger row navigation; clickable rows are not tab stops and must contain a named link.

## shell-navigation

The shell is a well-documented, accessibility-conscious desktop app squeezed onto a phone. Navigation gating (role, workspace mode, the post_scheduling flag), client-scope plumbing (cookie, ?clientId=, page handler, leave guards), sign-out purging and the skip-link/single-main contract are solid and should be kept. The phone layer is mostly the desktop chrome with things hidden.

Biggest mobile-first gaps:

1. There is no thumb-zone navigation. Every destination sits behind a top-right hamburger that opens a drawer from the left. Settings and Team take 3 taps because "More" starts collapsed.
2. The 56px phone top bar holds 4–5 identical 44px icon buttons. One of them, the health chip, is a colour-only dot. The only text left is the last breadcrumb, which repeats the h1, contradicts it, or is blank. There is no back/up control in the shell, so pages build their own (at least 6 different back patterns).
3. The shell is fixed to the viewport (h-svh) and the page scrolls inside a div. On phones this stops browser chrome from collapsing and stops tap-to-top and pull-to-refresh.
4. Global banners stack without limit and are not sticky, and there are three separate banner implementations. With a banner showing, the desktop workspace frame is taller than the window (its calc only subtracts the toolbar).
5. Tablets get a rail of icons with no labels, named only by hover tooltips.
6. The command palette, client switcher, account menu and Settings tabs are desktop popovers or tab strips with no phone form.
7. Destinations are defined in five separate lists that have drifted (Calendar and Notifications are missing in places).
8. No `viewport` export, so safe areas are unusable.

The React "Cannot update a component" error is real and traced. `useScopeReset` in QueryProvider (lib/queries/scope-reset.ts:161) subscribes to every QueryCache event and renders above HydrationBoundary, so its first committed snapshot is always stale. At ≥768 only, AppShell's `useMediaQuery(…, false)` flips after hydration. That forces the toolbar and OAuth Suspense boundaries to hydrate in the same pass. Each `useQuery` mount there emits a QueryCache notify during render, which schedules a setState on QueryProvider.

## inbox

The inbox's business logic is in very good shape and should be kept as it is. All view state lives in the URL. One status ladder (derivePrimaryAction/deriveReplyStatus) drives both the status line and the button. A single dirty-guard store protects unsaved replies and stashes them to sessionStorage. Publish is one press: it saves and verifies first and recovers from stale_draft_evidence. After a publish the inbox moves to the next review, puts focus on its heading and announces it. Viewers get no bulk tools, empty states are evidence-backed, and most tests couple to roles and names, not classes.

The presentation layer is a desktop two-pane design squeezed onto phones.

- At 360/390, Publishing, Failed and Done sit off-screen in the queue track. Nothing scrolls the active tab into view, so a client-hub link to queue=failed lands on an invisible active tab.
- The phone detail stacks the shell top bar, a row holding only a Back arrow, and a 112px sticky publish bar. That chrome is about 29% of 844px, and the textarea starts around y≈540.
- There are no prev/next controls, so on a phone the only way to skip a review is Back, then another tap.
- Nothing in the inbox reacts to the on-screen keyboard (no visualViewport handling, no viewport export). The fix that hides the status line while typing still leaves the 48px Publish button on screen. EditorFrame has a keyboard-safety hook the inbox does not use.
- The safe-area paddings do nothing, because the root layout never sets viewport-fit=cover.
- Several touch targets are under the system's own 44px rule: queue tabs 38px, filter segments 28px, Load more 24px, checkboxes 24px.
- Some explanations exist only in title tooltips, and the bulk "No reply needed" action runs with no confirm or undo.
- Viewers get a full composer and a sticky Publish bar, all disabled.
- The 768px width-only split leaves a 315px detail pane in portrait.
- Several primitives are re-implemented locally instead of using components/ui: ActionBar, SegmentedControl, LoadMore.

The React setState-in-render error seen at 768px and up comes from the shell (ClientScopeSync, ClientSwitcher, OAuthReturn), not from the inbox.

## listings-content

The listings area holds a lot of careful business logic. There is one area registry (lib/listings/areas.ts). LocationTab checks capabilities before any resource is fetched. Save here, Review changes and Publish to Google are kept apart, and diffs only say what the app can prove. Leave guards, draft stashing and focus-clear scrolling sit on top of that. The presentation layer, though, is a desktop workspace squeezed onto phones. At 390px the listing header (client eyebrow, listing name, serif h1 with pill, description, full-width sibling combobox, half-width Activity button, full-width 'Area:' dropdown, model note) fills about 370px of the 844px viewport. A floating dark footer then takes another 100–190px. On Opening hours not a single day row appears in the first viewport (listing-hours-chromium-light-390.png). Profile stacks four selector controls before the first field. Navigation differs by breakpoint. Phones get a dropdown that disables unavailable areas and always lists 'Review & publish'. Desktop gets a scrolling tab row that leaves unavailable areas navigable, omits Review & publish, and cuts off 'Sugges…' at 1280. There are two ways to publish (the per-area sheet and the cross-area /changes page), shown as two primary buttons on one screen. Editors use phone-hostile inputs: HH:MM fields that bring up the full text keyboard, a bulk hours grid that squeezes time inputs to about 45px at 360, and an 11-option segmented control with a hidden scrollbar. Status pills contradict each other ('In sync' in the header, 'No menu' in the editor). Area pages repeat a visible h2 under the h1. The shared confirm dialog's pending label says 'Sending to Google…' on actions that send nothing. Modal patterns are mixed (centred dialogs, nested dialog over dialog, bottom sheets), and there are three different filter widgets. No viewport-fit is set, so every safe-area padding resolves to 0. Bulk compose has no screenshot baseline (it renders as a 404 in the fixture), and mobile axe covers only the board. A mobile-first rebuild should keep the data, gating and publish contracts as they are, and replace the header and navigation, footer, inputs, filters and modals with a small set of mobile primitives.

## listing-admin-profile

This area has the heaviest business logic in the app: the Google profile editor (13 indexed sections plus about 7 unindexed blocks), people/access administration, location lifecycle (transfer/delete), and Google verification (start and PIN completion). Correctness and honesty are strong. Every Google write goes review → approve (with an optional second approver) → explicit consent → send → outcome checked independently, and uncertain sends block replays. Rosters read before a confirmed change are hidden instead of shown as current. Owner locks are explained in each row, and counts say "unavailable" rather than 0.

The mobile-first gaps are structural, not cosmetic:

1. Reviews show up far from the action that started them. Access and lifecycle reviews render at the top of the page, with no scroll or focus move, after a dialog at the bottom closes.
2. The profile is one very long scroll. Mobile navigation is a single non-sticky "Jump to section" Select whose order differs from the page order.
3. At 360 and 390 the profile footer bar takes about 21% of the viewport and covers the first field, even when there is nothing to do.
4. The primary content sits below the fold on all three routes: the roster and "Add administrator" on People, and PIN entry on Verification.
5. The PIN field is a masked password input with no numeric keypad, and it has to be typed twice.
6. Google resource IDs and confirmation names are free text with case-sensitive checks and no autocapitalize or autocorrect hints.
7. Every form dialog is a centred modal on phones.

The same review → confirm → outcome flow is built separately at least seven times. There are 5 controller hooks, 4 summary-list layouts, 5 sets of outcome wording, 7 saved-work lists and 2 almost identical approval sheets. Existing primitives that fit (OperationOutcome, Stepper, ChoiceCard, SegmentedControl) go unused. These should become one ReviewedWrite primitive (a bottom sheet with a step indicator), one SavedWork list and one OutcomeSummary. Two modules are reached only by tests (voice-of-merchant.tsx, verification.tsx), and the AdminsTable invitations branch never runs.

## settings-setup-auth

The auth screens are the most phone-ready part of this area. AuthCard puts a single-column card at 900px and below, and the forms use proper autocomplete, inputMode, autoCapitalize and one-time-code. Focus management, the double-submit guard and the rules against revealing which emails have accounts are already solid. The setup wizard also adapts to phones: under 720px it shows "Step N of M", a progress bar and an "All steps" disclosure, its footer sticks to the bottom with safe-area padding, and Continue stays enabled but shows a ValidationSummary when the step isn't ready.

Settings is desktop-first. There is no settings index: /settings opens the Reply policy form for every role, including viewers who can't edit it. Up to 8 areas sit in one horizontal tab row that mixes personal and workspace settings. On a 360px screen the TabNav never scrolls the current tab into view, so on Billing, Usage and Operations the active tab is off-screen.

The policy save bar is always pinned and takes about 110px of the screen. Feedback for saves and actions appears at the top of long pages, out of view. Form-heavy dialogs (invite, client access, privacy, MFA step-up) stay centred modals; the bottom-sheet primitive has 0 uses in this area. There are four different ways of saving.

Setting up two-step verification on a phone is awkward: the screen shows only a QR code and the secret as plain text. The API returns an otpauth `uri` that the UI never uses.

The Listings step embeds a 3,014-line onboarding mega-form full of free-text codes (country, language, currency, HH:MM times, place IDs).

Concrete bugs: on /privacy a long `<code>` URL overflows the page horizontally (WCAG 1.4.10 failure, which the sweep missed), and at 360px the members card overlaps "Can publish" with the Joined date.

Lots of local re-implementations: Section/description-list wrappers, access-scope pickers, loading/error states, the segmented control and OTP inputs. Two baselines are 404s because their feature flags are off (security, privacy), and none of the wizard steps were captured.

## mobile-ux-live

At 360-390px the product works without page-level overflow and has some good phone patterns: the inbox swaps list and detail and keeps URL state, focus and scroll position; the publish bar is pinned to the bottom with a full-width 48px button; touch controls are 44px with 16px field text; right-hand sheets turn into bottom sheets; toasts sit at the top; empty states are clear; the hours editor and calendar respond to their container. Overall, though, it reads as a compressed desktop console rather than a phone design.

Biggest gaps:

1. **Navigation is hamburger-only.** The menu sits top-right. Team and Settings are hidden behind a "More" disclosure inside the drawer, Notifications is only reachable through the bell, and on phones the breadcrumb shrinks to the current page, so there is no "up" link.
2. **The shell is viewport-locked with an inner scroll column.** The document never scrolls (30 of 36 full-page shots are exactly 844px tall), which loses browser-chrome collapse, tap-to-top and pull-to-refresh. `viewport-fit=cover` is never set, so all `env(safe-area-*)` padding resolves to 0 on iOS.
3. **Every listing area stacks 3–4 controls and an explanatory note above the content.** On Opening hours the first day row is not visible in the 844px viewport.
4. **Commit bars show even when nothing has changed.** The editor and settings bars stay on screen when clean and cover 100–190px; the save pattern differs across five surfaces.
5. **Horizontal tabs and segmented controls clip without any signal.** On Settings › Operations, Usage and Billing the current tab is scrolled off-screen.
6. **Tables become label/value cards.** Only about two rows fit per screen, the first-cell labels repeat the obvious, and at 360px a pill overlaps the date next to it.
7. **Text and targets are small.** The default UI text is 13px, there are 51 literal sizes under 12px, and inbox checkboxes are 24px targets.
8. **Dialogs and menus are centred desktop overlays.** The bottom-sheet grabber is decorative; there is no drag-to-dismiss.

Dark mode is coherent, with two exceptions: the inverted near-white action bar, and a disabled "Publish reply" that reads as enabled. Bulk, settings/security and settings/privacy were baselined as 404s because their feature flags are off, so they need re-capture.

### Business logic a rebuild must preserve

- Role gating: viewer inbox has no selection checkboxes and no Sync (inbox-viewer vs inbox 390). Team is adminOnly in MORE_ITEMS (nav.tsx:67-74). Settings tabs are filtered by capability, MFA flag, billing flag and owner (settings-nav.tsx:28-93). Bulk is owner/admin only plus the bulk_actions flag (listings/bulk/page.tsx:13-16).
- Feature flags that remove destinations: Calendar is hidden when post_scheduling is off (layout.tsx hideCalendar; nav.tsx navItemsFor). Settings security and privacy return 404 unless MFA_ENABLED or privacy_settings is on. Business mode removes Clients and the client switcher (nav.tsx:52-58, topbar.tsx:54).
- Inbox URL state: ?selected=<id> drives list/detail on phones; browser Back returns to the list; focus moves to 'Back to reviews' on open and returns to the originating row; page and list scroll positions are restored (inbox-view.tsx:585-599, 846-875).
- Inbox publish gating: the 'a' hotkey asks the action bar to press its own main button rather than publishing directly (inbox-view.tsx:600-604). Publish stays disabled for users who cannot publish, for unsaved composer edits and for stale drafts that fail re-check (tests/components/action-bar.test.tsx). Auto-advance runs after publish (inbox-view.tsx:425-437).
- Editor approval boundary: 'Save here' writes only the NabaPresence copy; 'Review changes' opens the diff sheet; only the sheet's 'Publish to Google' sends anything. Discard only affects local edits. Viewers get a read-only reason bar with no buttons (editor-footer.tsx:30-45, 111-128, 172-206).
- useReportEditorStatus keeps the area header pill consistent with the footer (editor-footer.tsx:97-109). Hiding or collapsing the bar must still report status.
- Dirty guards on navigation (tests/components/use-dirty-guard.test.tsx) and the per-page dirty context (components/inbox/dirty-context.tsx) must intercept bottom-nav and back taps as well as the drawer.
- Client scope: ?clientId= in URLs plus the scope cookie (lib/clients/scope.ts), ClientScopeSync in the toolbar and withClientScope on nav links. A new bottom nav must carry the remembered client.
- Nav modal semantics: focus trap, Escape and scrim close, focus returns to the toggle, closes on any route change and when the viewport grows past 768 (app-shell.tsx:245-293, 349-359).
- Focus Not Obscured: useKeepFocusClear keeps focused fields clear of the sticky toolbar and footer (editor-frame.tsx:10); any new app bar or bottom nav height must be fed into it.
- Health announcements: HealthAnnouncer speaks only changes in connection health (context-health-chip.tsx:104-127). Keep it if the chip moves.
- Command palette with ⌘K/Ctrl K and the client-switch commands (command-palette.tsx), plus inbox hotkeys j/k/r/g/a and selection keys for non-viewers (inbox-view.tsx:604-650).
- Coarse-pointer guarantees: 44px controls and fields, and 16px field text to stop iOS zoom (globals.css:635-644).
- Toasts top-anchored on phones with footer clearance for sheets and dialogs (toast.tsx:28-60, 106).
- DataTable semantics: mandatory sr-only caption, row click as a pointer convenience with a named link in a cell, and checkbox clicks stopping propagation (data-table.tsx:72-75, 155-178).
- Listing area access: disabled areas carry unavailableReason and badges with pending counts (area-frame.tsx:155-221); 'Review & publish (n)' stays reachable from every area while edits wait.
