Worktree `/tmp/naba-presence-p1` @ `e4123d25` (branch `ux/flows-presence-p1`). Analysis only; nothing was run.

## 1. Flow ID, name, start and end

- **ID / name:** p1-F01, sign in with email and password at `/sign-in`.
- **Entry points:** `/` when signed out (`app/page.tsx:9`); the dashboard layout's signed-out redirect `signInPathFor(requested)`, which gives `/sign-in?next=…` (`app/(dashboard)/layout.tsx:45`, `lib/api/next-path.ts:35-39`); a foreground 401 from `apiFetch` (`lib/api/client.ts:290`); "Back to sign in" links on every auth card; the brand mark (`components/auth/auth-card.tsx:122,232`); sign-out (`components/app-shell/account-menu.tsx:153,181`); a failed confirmation link (`app/auth/confirm/route.ts:29-38`); the legacy `/login?…` alias, which forwards its query (`next.config.ts:76`, `tests/e2e/routing.spec.ts:224-235`). Current invitation emails link to `/invite/{token}` (`lib/server/invitations/delivery.ts:350`). `/sign-in?invite=` is only reached through a legacy or hand-built URL.
- **Success exits:** a full navigation to `next ?? "/inbox"` (`components/auth/sign-in-form.tsx:201-205`), or to `/sign-in/verify[?next=]` when MFA is required (`:202-203`).
- **Boundaries:** create-account (F02) shares the form and the segmented control (`sign-in-form.tsx:330-349`). The resend disclosure (F03) sits at `:479-501`. Forgot password is reached through the link at `:427-435`. The MFA code screen is `app/(auth)/sign-in/verify/page.tsx`.

## 2. Steps today

1. **The server renders the page.** `sanitiseNextPath(params.next)` runs, then `getSession()`. A visitor who is already signed in gets `redirect(nextPath ?? "/inbox")` and never sees the form (`app/(auth)/sign-in/page.tsx:21-24`). In that case `?invite=` is ignored silently. `?status=` goes through `confirmStatusMessage` (`:36-38`). `registrationAllowed` is `REGISTRATION_MODE === "open" || invite` (`:30-32`; the default is `open`, `lib/server/env.ts:219-222`). **The page never reads `PASSWORD_AUTH_ENABLED`**, so the form looks the same whether password sign-in is on or off.
2. **Panel.** It shows the eyebrow "Welcome back", the h1 "Sign in to NabaPresence" and "Your Google reviews and Business Profiles, from one inbox." (`components/auth/sign-in-panel.tsx:11-15`). With `?invite=` and no status it also shows an info Alert: "Sign in to accept your invitation / Use the email address the invitation was sent to. You’ll join straight after." (`:76-84`). The footer reads "Access is by invitation or a new account." (`:68-70`).
3. **Form, top to bottom.** A status or error alert inside a focusable wrapper (`sign-in-form.tsx:319-323`), the Sign in / Create account toggle (`:330-349`), "Email address" (`type=email`, `autocomplete=username`, `:393-416`), and "Password" with a "Forgot password?" link beside the label (`:418-437`). The password field has a show/hide toggle (44px on touch) and a "Caps Lock is on." hint (`components/auth/password-field.tsx:58-61,67-101`). Then the "Sign in" button, the line "After signing in you’ll go back to `<next>`." when `next` is set and is not `/inbox` (`:469-477`), and the disclosure "Didn't receive a confirmation email?" (`:488-500`).
4. **Focus in the form** starts the zod schemas loading (`:98,315`). Submit waits for them (`:168-177`).
5. **Local validation** with `loginSchema` (`lib/domain/auth.ts:42-48`). Messages: "Enter your email address.", "Enter an email address like name@example.co.uk." and "Enter your password." (`sign-in-form.tsx:60-78`). Focus moves to the first invalid field (`:185-193`). Nothing is sent.
6. **Submit.** `POST /api/auth/password/login` with `{email,password,inviteToken?}` and an `Idempotency-Key` (`lib/api/auth.ts:19-28`, `lib/api/client.ts:312-316`). The button becomes `disabled` with the label "Signing in…" (`sign-in-form.tsx:453-467`). The inputs stay editable.
7. **Server.** The route checks same origin, then parses the body (400 `invalid_request`), then applies the abuse budget `login` (IP 30 and email 90 per 15 minutes; 429 `auth_rate_limited` with `details.retryAfter`) (`app/api/auth/password/login/route.ts:8-13`, `lib/server/route.ts:443-497`, `lib/server/abuse-limits.ts:63-67,412-418`). Next is `signInWithPassword`, which throws 503 `password_auth_disabled` when the flag is off and 503 `auth_provider_unavailable` when Supabase is not configured (`lib/server/password-auth.ts:86-101`). An unverified email, a provider 400/401 and a provider 429 all fold into 401 `invalid_credentials` (`:191-216,240-241`). `completeEmailAuthentication` then accepts any invite and sets the session or the MFA ticket. The response is `{authenticated, mfaRequired}` (`route.ts:23-26`).
8. **Success.** `window.location.assign(...)`, followed by a promise that never resolves, so the button stays pending until the page unloads (`sign-in-form.tsx:201-210`).
9. **Failure.** `fieldErrorsFrom` + `authErrorMessage(error,"sign-in")` (`:211-217`, `lib/api/auth-errors.ts:175-208`). Focus goes to the first field with an error, or to the alert wrapper when no field has one (`sign-in-form.tsx:151-155`). Typed values are kept.

## 4. Protected rules

- `next` is sanitised on the server page and the client never parses it again (`sign-in/page.tsx:22`, `lib/api/next-path.ts:9-22`). The MFA handoff carries only the sanitised value (`sign-in-form.tsx:203`).
- Login never reveals whether an account exists or is verified. Unverified, 400/401 and provider 429 all fold into `invalid_credentials` (`lib/server/password-auth.ts:186-216,240-241`). The resend disclosure is always present and never depends on an error (D3, `sign-in-form.tsx:479-487`).
- The abuse budget runs before the handler (`lib/server/route.ts:491-497`, `abuse-limits.ts:63-67`). The kill switch lives in `providerConfiguration` (`password-auth.ts:86-93`).
- Double submit is blocked by `pending || validating.current` and a promise that never resolves after success (`sign-in-form.tsx:166-177,206-210`).
- Server authority: navigation happens only after a 2xx (`:198-205`).
- The typed email goes to Forgot password through sessionStorage, never the URL (`sign-in-form.tsx:429-431`, `lib/api/reset-email.ts:1-16`).
- The confirmation-link failure redirect and its `status` code belong to the route handler (`app/auth/confirm/route.ts:29-38`).
- Invite acceptance happens only inside `completeEmailAuthentication` with the posted `inviteToken` (`login/route.ts:15-22`).

## 7. Proposed changes

**C1. Make each attempt's answer new (fixes #1).** Files: `components/auth/sign-in-form.tsx`.
- In `submitWith`, sign-in branch, clear the old answer before validating: add `setMessage(null)` as the first statement of the `mode === "sign-in"` block (line 184). This replaces the stale banner on a local-validation failure and on a valid submit. Do the same in the create-account branch (line 222) for parity.
- Change the focus effect so it reacts only to a newly arrived message. Deps become `[message]`. Read the current field errors through a ref (`fieldErrorsRef.current = fieldErrors` on render) or compute `hasFieldErrors` in the catch and focus there. Behaviour: `message` goes from null to an object, the alert remounts, `role="alert"` announces it, and focus moves to it when no field is to blame.
- Benefit: the banner disappears when you retry, and a new banner with focus marks a new server answer. Nothing is read before the server replies. Principle: Nielsen #1; HIG consistent feedback; WCAG 4.1.3 Status Messages, 3.3.1 Error Identification.
- Risk: none to protected behaviour. Same request, same codes, same double-submit guard. Trade-off: the form moves up by the banner's height while pending; the button is disabled, so a stray tap does nothing. Not a shared file.

**C2. Name connection and outage failures (fixes #2, #3).** Files: `lib/api/auth-errors.ts` (area file, auth surfaces only).
- Add to `BY_CODE`: `network_error: { title: "We couldn’t reach NabaPresence.", description: "Check your connection and try again." }`.
- In `authErrorMessage`, after `messageForCode(...)` returns undefined, fall back to the surface outage copy for server failures: `if (error.status >= 500) return { ...BY_CODE.auth_provider_unavailable, title: UNAVAILABLE_TITLE[surface] }`. Otherwise return `GENERIC`.
- Benefit: people know whether to check their connection or wait. Principle: Nielsen #9; WCAG 3.3.3 Error Suggestion. Risk: copy only. It does not reveal whether an account exists, because the codes are not account-dependent. Callers: every auth form plus `resend-confirmation-button.tsx:69`. No `components/ui` change.

**C3. Point a failed confirmation link at the right recovery (fixes #4).** Files: `lib/api/auth-errors.ts`, `components/auth/sign-in-form.tsx`.
- Add a sign-in-only override in `confirmStatusMessage`. When `surface === "sign-in"` and the resolved code is `invalid_email_link` (including the unknown-code fallback), return `{ title: "That confirmation link is invalid or has expired.", description: "Invited to a team? Open the invitation link again. Otherwise, enter your email below and send a new confirmation link. Already confirmed? Just sign in." }` with no `action`. `/reset-password` keeps its own mapping because it calls `authErrorMessage` with its own surface.
- In `SignInForm`, add the prop `openResendHelp?: boolean` and render `<details open={openResendHelp} …>` (line 488). `SignInPanel` passes `openResendHelp={params.status === "invalid_email_link" || unknown}`. Compute this in `page.tsx` as `status && !(status in known codes)`, or export an `isLinkFailureStatus(status)` helper from `auth-errors.ts`.
- Benefit: the recovery that matches the problem sits next to the explanation, and nobody resets a password they just set. Principle: Nielsen #9 and #6; HIG preserved context. Risk: the disclosure still renders unconditionally; only its initial open state follows the **URL**, not the account, so D3 holds. No route change. Coordinate with F03, which owns the disclosure internals.

**C4. Banner matches the mode (fixes #5).** File: `components/auth/sign-in-panel.tsx:76`. Change the condition to `inviteToken && !statusMessage && mode === "sign-in"`. ## 8. Explicitly not proposed

- **Showing the unavailable notice before submit when `PASSWORD_AUTH_ENABLED=false` (#10).** It reads an existing flag and is not a new one. But it changes every harness capture and spec of `/sign-in` (both run with the flag off), and the copy for a deliberate shutdown is a product decision. Owner decision.
- **Carrying `inviteToken` (and `next`) through `signInError` in `/auth/confirm`.** Today a failed invited confirmation lands on sign-in without the invitation (`auth/confirm/route.ts:30-37`). The fix is a protected route-handler change, so it goes to the owner. C3's copy points invitees back to their invitation link in the meantime.
- **Sending a signed-in `?invite=` visitor to `/invite/{token}` (#11).** This would be a page redirect, but it touches the invite-token flow, and current emails already use `/invite/{token}`. Low reach. Owner decision if the legacy links matter.
- **Moving "Forgot password?" after the field** to fix the Email → link → Password tab order. It is a familiar pattern and a password manager fills both fields; the benefit is low.
- **A softer tone for `sign_out_everywhere_failed`.** The requested action did fail, so destructive is honest.
- **Friendlier wording for server-side `invalid_request` field messages (S13).** Rare: the client parses first.
- **Any change to the neutral `invalid_credentials` copy, the always-present resend disclosure, or the folding of 429 into `invalid_credentials`.** These are protected (D3).
