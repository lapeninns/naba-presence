# p4-F08: Review Google's suggested updates (`/listings/[id]/suggestions`)

Mapped read-only against `/tmp/naba-presence-p4` at `e4123d25`. Nothing was run. Paths are repo-relative. Items marked "Hypothesis" come from reading the code and were not seen in a browser.

**Premise correction:** Accept does **not** write to Google. Every decision (apply, ignore, keep_local, delete_local) changes only NabaPresence's canonical copy. The copy says so (`suggestions-page.tsx:264-267`, `suggestion-list.tsx:114-136`) and so does the area note (`lib/listings/areas.ts:162-163`, model `inbound`). Google is only _read_, by "Check Google now". The protected rules below are therefore about local data integrity: role, confirmation literal, optimistic lock, claim, overwrite acknowledgement and audit.

## 1. Start / end

- **Start:** the "Suggested updates" area tab or card (`lib/listings/areas.ts:117-124`, `capability: "profile"`), the overview card "Review Suggested updates" (`tests/components/listing-area-cards.test.tsx:88-91`), or a deep link. Page: `app/(dashboard)/listings/[id]/suggestions/page.tsx:20-35`. `StreamedTab` prefetches the profile and both proposal lists on a document load (`lib/server/prefetch.ts:1019-1046`). The fallback reads "Reading the suggested updates from Google…" (`streamed-tab.tsx:49`, `lib/locations/gating.ts:136-137`). The editor is `SuggestionsTab`, loaded via `components/listings/area-frame.tsx:945-950` (shared).
- **End:** every pending suggestion has been accepted, ignored, kept or removed, and the server has confirmed each one. The page then shows "No suggestions from Google". Or the operator leaves with suggestions still waiting.
- **Boundaries:** publishing the result ("Ignore keeps yours… next publish puts yours back") belongs to F09 (`/changes`). Editing the field by hand belongs to the profile and menu editors ("Open business profile" / "Open food menu", `suggestion-list.tsx:257-264`).

## 3. Baseline steps (taps)

1. Open the area: 1 tap from the strip or card. The streamed fallback shows first, then the skeleton (`suggestions-page.tsx:51-72`) while the two lists load.
2. **No suggestions:** "Check Google now" takes 1 tap. The button shows "Checking…", then an info toast. Re-checking from a populated page uses "Refresh from Google" (ghost, sm).
3. **Per row:** read "Here now" against "On Google" (`DiffView`), then:
   - Accept or Ignore: 1 tap. The row disappears after the refetch (`use-import-review.ts:55`).
   - Accept with "Also edited here", or a whole-menu `structure_changed` row: Accept, tick "I understand this changes my local data.", then Accept again. That is 3 taps (`suggestion-list.tsx:245-255,468-500`).
   - An item missing on Google: "Keep here" or "Remove here", 1 tap each. Remove has no confirmation unless the row is in conflict (Hypothesis P3: removing a local menu item has no undo).
4. **Failure:** the inline "Not applied" message, the reason and Retry (`:368-390`). Retry takes 1 tap.
5. Audit count: "Check Google now" took 1 tap, measured from code. Accept and ignore were not captured because the fixture had no suggestions (`results.md:415`, `findings.md:442,749`).

## 5. Protected rules (preserve)

1. **Owner/admin only** for decisions and refresh: `decision/route.ts:19`, `refresh/route.ts:22`. The UI gates may be added or tightened, never relaxed.
2. **Confirmation literal** per surface: built by the client at `lib/api/location-import-review.ts:58`, defined in `lib/contracts/location-import-review.ts:58-64`, cross-checked on the server at `decision/route.ts:43-49`.
3. **Optimistic lock** `expectedCanonicalRevision`: profile `lib/server/import-review.ts:925-930`, menu `:1042-1046` (each compares against _its own_ `presence_canonical_resource` row, `:1028-1032`).
4. **Claim before act** (no double decision): `pending → processing` at `import-review.ts:739-770`, then 404 / `proposal_superseded` / `proposal_not_pending`. Releasable failures go back to pending (`:714-717,862-875`). Others become terminal `failed` (`:877-879`).
5. **Overwrite acknowledgement:** enforced on the server at `:789-798`; the client asks first at `suggestion-list.tsx:245-255` and the dialog requires a tick (`:488-489`).
6. **Audit write** on every decision: `import-review.ts:837-851`.
7. **Server authority:** a success toast only in `onSuccess` (`suggestion-list.tsx:204-218`). Rows leave only by refetch after the request settles (`use-import-review.ts:55`). Never show "accepted" optimistically.
8. **Truthful direction copy:** nothing goes to Google. Keep "Nothing was sent to Google" wherever accept or remove is described.
9. **Rate limit and kill switch** on refresh (`refresh/route.ts:26-38`). Don't add auto-refresh loops.

## 8. Proposed changes

1. **Use the menu's own revision for menu decisions (F-1, P1).**
   - **Change:** in `components/locations/suggestions/suggestions-page.tsx`, render the food-menu `SuggestionList` through a small local `MenuSuggestions` wrapper, mounted only when `pendingMenu.length > 0`. The wrapper calls `useFoodMenus(locationId)` (`lib/queries/use-location-menu.ts:10`) and passes `foodMenus.canonicalResource.revision`. While that read is pending, its decision buttons are disabled with the reason "Loading the food menu…". On error it shows an inline retry. The profile list keeps the profile revision.
   - **Benefit:** menu suggestions can be decided at all.
   - **Principle:** Nielsen #9 (help users recover; a Retry that can never succeed is not recovery).
   - **Shared:** none required. Optionally add a `readFoodMenus` entry to `suggestionsTabPrefetch` (`lib/server/prefetch.ts:1024`, **shared**, flag it), only when the menu list is non-empty. That costs one more Google read, so skip it in this pass.
   - **Server untouched.** Verify first with a focused unit test (§9), and record it as a core-defect fix in the report.
2. **Gate the check buttons and say the right reason (F-2, F-3, P2).**
   - **Change:** in `suggestions-page.tsx`, give both refresh buttons `disabledReason={checkReason}`, where `checkReason` is "Only owners and admins can check Google for suggestions." when the role gate applies, else `editReason` (billing). Make the banner title come from the reason: keep the role copy, and show `editReason` for billing (for example the title "Suggestions can’t be decided right now" with `{editReason}` as the description). In `suggestion-list.tsx:184-186`, use the role copy only when `editDisabledReason` is the role reason; otherwise pass `editDisabledReason` through.
   - **Benefit:** no dead-end 403, and an honest reason.
   - **Principle:** HIG (disabled controls explain themselves); Nielsen #5 (error prevention); WCAG 3.3.2.
3. **Report what the check found (F-4, P2).**
   - **Change:** in `refreshFromGoogle` `onSuccess: (data) =>`, compute `raised = (data.outcomes.profile?.raised ?? 0) + (data.outcomes.foodMenus?.raised ?? 0)`. Show "Checked with Google" with the description "Nothing new since the last check." when 0, or "{n} new suggestion(s) to review." when more (use `countNoun`, `components/ui/count-text.ts:39`). Keep the `info` type.
   - **Benefit:** the check's outcome is visible.
   - **Principle:** Nielsen #1 (visibility of system status); WCAG 4.1.3 (the toast is a status message).
   - **Server authority:** the copy comes from the response.
4. **Settle rows from the server's answer (F-5, P2).**
   - **Change:** in `suggestion-list.tsx`, keep a local `settled: Set<string>`. Add the id in `onSuccess` (server-confirmed) and keep that row's buttons disabled (or hide the row) until the refetch removes it. Hold `disabled` while `useIsFetching(locationImportReview)` is non-zero for the row just decided. For a terminal failure (code not `canonical_resource_stale`), make the error toast title `${proposalTitle(proposal)}: ${message}` and add the description "Check Google now to load the latest suggestions." Drop the duplicate toast when the inline alert will stay visible (releasable codes).
   - **Benefit:** no phantom second decision, and you can tell which suggestion failed.
   - **Principle:** Nielsen #1 and #9; HIG (consistent feedback).
   - **Protected:** nothing is shown as accepted before `onSuccess`.
5. **Trim the repetition (F-6, P3).**
   - **Change:** in `suggestions-page.tsx:223-230`, omit zero parts ("2 suggestions waiting · 2 business profile"), using `countNoun`. Rename "Refresh from Google" to "Check Google now" (one name for one action). In `suggestion-list.tsx:454-458`, move the Accept/Ignore explanation to once per group, under the group label, and keep "Only changes NabaPresence’s copy." for missing rows. Keep the page footnote, which carries the protected direction copy.
   - **Benefit:** a shorter scan per row on a 390 px screen.
   - **Principle:** HIG simplicity and hierarchy; Nielsen #8.
6. **Announce loading and errors (F-7 and F-8, P3).**
   - **Change:** in `suggestions-page.tsx:53`, add an `sr-only` `role="status"` "Loading suggested updates…" to the skeleton. Pass `role="alert"` to the error `Empty` (`components/ui/empty.tsx:92` supports it). In `suggestion-list.tsx`, add `pendingLabel="Keeping…"` / `"Removing…"`.
   - **Principle:** WCAG 2.2 SC 4.1.3 (status messages); HIG feedback.
   - **Not proposed:** a confirmation for F-8 "Remove here", because it changes the flow's step count. List it as a follow-up.

All changes are in this flow's two components. Shared files are untouched unless change 1's optional prefetch is taken (`lib/server/prefetch.ts`). No API, contract, migration or flag changes.
