## 3. Baseline steps

1. Open the area. The streamed fallback shows "Reading the verification from Google…". Then the session check, then the workspace.
2. Workspace order (`verification-tab.tsx:71-90`):
   - **Verified, nothing pending** (`verifiedAtRest`, `:73-74`): the status card, then a collapsed "Verification tools" disclosure (PIN, start, guidance, history).
   - **PIN expected** (`pinExpected`, `:46`): PIN, status, start, guidance, history.
   - **Otherwise:** status, PIN, start, guidance, history.
3. Status card (`verification-observation.tsx:69-123`): a headline, the action line, "Last checked {Instant}", and a collapsed "More about this".
4. Re-checking Google: the only control is "Check current Google verification state", which lives in the PIN section (`verification-completion.tsx:127-149`). On a verified listing that section is inside the collapsed tools. Re-checking takes 1 tap on the page, or 2 when verified.

## 5. Protected rules

- The page says "Verified" only when Google returns `hasVoiceOfMerchant === true` (`verification-observation.tsx:58-62`). `verifiedAtRest` also needs no error and nothing pending (`verification-tab.tsx:73-74`).
- Contradictory provider states are treated as unknown, never as verified (`lib/domain/google-verification-state.ts:42`). Provider state maps to a request phase only, never to the listing's verified status (`:27`; test `tests/google-verification-state.test.ts:9`).
- A failed merchant read keeps the history and reports unknown (`lib/server/google-verification-state.ts:62-70`). A failed history read fails the whole read (`:38-61`).
- An error never reads as "not verified": the copy at `verification-tab.tsx:51` says so. E2E asserts that "Not verified" has count 0 in the unknown and disconnected states (`tests/e2e/verification-workspace.spec.ts:96,191`).
- A request that Google reports as failed never gets the confirmed tone (`verification-attempt-status.tsx:114-135`). Finishing a request is not the same as being verified (`verification-tab.tsx:67`).
- Writes are gated: `writeReason` blocks sends whenever the observation or caps are missing (`verification-tab.tsx:32-42`). The server refuses a start on a verified listing (`lib/server/google-verification-execution.ts:137`).
- Provider error text never reaches the UI (tests `tests/components/verification-tab.test.tsx:141,153`).
- F10 is read-only. It makes no audit writes. The audit, review and approval writes are in F11 and F12 (the execute routes). Changing them is out of scope.

## 7. Friction

1. **P1: the error state has no retry where the error is shown, and it doesn't say why.** The alert at `verification-tab.tsx:51` tells the operator to "use the current-state check on this page". That button is in the PIN section (`verification-completion.tsx:127-136`), after the PIN lines. A `google_reconnect_required` 409 (`lib/server/google-verification-state.ts:22`) shows the same generic copy, with no "Reconnect" path. The mapped copy already exists ("Google access has expired. Reconnect this account to continue.", `lib/errors/action-errors.ts:496-497`). Nielsen #9 (help users recover); WCAG 3.3.1.
2. **P1: one failure produces three warnings.** With no data there is the "Verification changes are paused … Check current Google verification state before reviewing…" banner (`verification-tab.tsx:42,80`), the status alert (`:51`), and the PIN-section line "Current Google state could not be refreshed…" (`verification-completion.tsx:143-148`). Nielsen #8.
3. **P2: the loading state says things that aren't known yet (Hypothesis, on a client navigation with a cold cache).** While `current.isPending`, `writeReason` is set (`verification-tab.tsx:41-42`), so the yellow "Verification changes are paused" banner shows. While caps are pending, the reason is "Checking current publishing permissions." (`:35`). The PIN section receives `[]` and says "Google has no PIN request waiting for this listing." (`verification-completion.tsx:112-114,315-320`) before Google has answered. That is a statement that isn't true yet. Nielsen #1; WCAG 4.1.3.
4. **P2: the status card has no status mark, and re-checking is hidden.** Verified, not verified and unknown differ only in their sentence (`verification-observation.tsx:76-88`). The overview uses a tone pill, "Verified" (healthy) or "Not verified" (attention) (`lib/listings/area-state.ts:241-252`). The header pill is off for this area (`area-frame.tsx:811`). "Last checked" has no "Check again" beside it. On a verified listing, re-checking means opening "Verification tools". Nielsen #1 and #4; WCAG 1.4.1 (the state is not carried by colour; the pill adds a word).
5. **P2: an unverified listing with nothing pending puts the PIN tools before the next step.** Action `verify` with no pending request keeps the order status, PIN, start (`verification-tab.tsx:76`). The operator first reads "Google has no PIN request waiting…" and sees "Continue verification in Google" before reaching "Start a new verification". The copy at `ownership_conflict`, `guidelines` and `unknown` says "Continue in Google" or "Check the listing in Google" (`verification-observation.tsx:25-30`), but the card has no link. The link is in the PIN section (`verification-completion.tsx:396-404`). Nielsen #6 and #7; HIG (primary action near the content it acts on).
6. **P3: "merchant standing" jargon remains** in the saved-outcome card (`verification-attempt-status.tsx:42,86,98`, and "independently observed" at `:82`). Nielsen #2.

## 8. Proposed changes (all in this flow's files unless flagged; no API, state-machine, gate or audit change)

**C1. A retry and a reconnect path inside the error alert, and one message instead of three (fixes friction 1 and 2).**

- **Change:** in `verification-tab.tsx:51`, add `<Button variant="secondary" disabled={current.isFetching} onClick={() => void current.refetch()}>Check Google again</Button>`. When `current.error instanceof ApiClientError && (current.error.reconnectRequired || current.error.code === "google_reconnect_required")`, use the description "Google access has expired. Reconnect the account, then check again." and add `<Link href="/settings/connections" className={buttonVariants({variant:"secondary"})}>Reconnect Google</Link>`.
- At `:80`, render the paused banner only when `reason` (the caps-derived value) is set. When only the observation is missing, append "Changes stay paused until Google can be read." to the status alert. `writeReason` still goes to the provider unchanged, so gating does not change.
- Keep "This does not mean the listing is unverified…".
- **Benefit:** a 1-tap retry where the operator is already looking, and a named recovery for the commonest cause.
- **Principle:** Nielsen #9 and #8; WCAG 3.3.1.

- **Principle:** Nielsen #1; WCAG 4.1.3.

**C3. A status pill and an in-place re-check on the card (fixes friction 4).**
