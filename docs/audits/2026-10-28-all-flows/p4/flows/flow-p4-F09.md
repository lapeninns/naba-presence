## 1. Start and end

- **Entry points:**
  - The header action "Review & publish (n)" on every listing page (`components/listings/area-frame.tsx:359-382`).
  - The phone's ⋯ overflow (`area-frame.tsx:404-415,469-472`).
  - The area list step (`lib/listings/area-nav.ts:135-140`).
  - A direct link.
  - The link is hidden when Google can't be reached, when nothing is pending, or when `canReviewChanges` is false (`area-nav.ts:75-82`).
- **Route:** `app/(dashboard)/listings/[id]/changes/page.tsx:21-35` renders `StreamedTab` with `changesTabPrefetch`, then `AreaEditor area="changes"`. The title is "Review & publish" (`:13`). The frame's lead copy is "What you have saved here, compared with what Google has now, before anything is published." (`area-frame.tsx:123-124`).
- **Successful end:** the done state shows a `PublishSteps` result list plus an `Empty` with "Back to listing" (`RP:521-566`), and a toast from `successToast` (`RP:435`).
- **Other ends:** the failure banner plus "Retry publishing" (`RP:708-729,777-778`), or "Nothing to publish" (`RP:540`).

## 3. Baseline steps (owner, one area, no conflict)

1. Tap "Review & publish (1)" in the header. On a phone it is two taps: ⋯, then the item.
2. Read the diff.
3. Tap "Publish 1 area to Google". Step-up MFA may interpose.
4. Done: read the result, then tap "Back to listing".

That is 2 taps on desk (3 on phone) plus 1 to leave. Each extra:

- A Google conflict adds 1 (tick "I've read what Google has now and want to replace it.").
- Leaving out an area adds 1 per area (the include checkbox).
- Recovering from a failure adds 1 ("Retry publishing").

These counts match the 15 Oct table (findings.md:445, "Publish: 3").

## 5. Protected rules (don't change behaviour)

- **Consent:**
  - The conflict ack is required. Its gate is `RP:477-478`, and it resets whenever the reviewed rows change (`RP:401-406`).
  - The ack is sent as `confirmOverwriteGoogleChanges` (`review-publish-reads.ts:110,177`).
  - Profile confirmation literal: `reads.ts:105`, checked server-side at `profile/route.ts:79-85`.
- **Overwrite and drift:**
  - Each step is pinned to the revision and hashes read for the page (`reads.ts:107-109,173-176,220-222`), with no re-read at publish time (test `tests/components/review-publish.test.tsx:75`).
  - Hours publish only the parts shown (`reads.ts:145-151`).
  - A blocked hours area is never queued (`reads.ts:152-164`, `RP:383-385`).
- **Server authority:**
  - A step says "Live" only from `stepOutcome`, for a verified endpoint (`use-publish-flow.ts:125-130`, `RP:281-293`).
  - A change-set answer short of confirmed counts as a failure (`use-publish-flow.ts:240-243`).
  - The rule "do not simulate progress" (`publish-steps.tsx:29-31`).
- **Idempotency:** the intent id is carried for unconfirmed attempts (`use-publish-flow.ts:191-195,222-233,266-268`), and each run uses `intent.idFor(body)` (`reads.ts:113,181,225`).
- **Order and stop:** the first failure stops the rest (`use-publish-flow.ts:296`), and queries are invalidated either way (`:300-301`).
- **Role gates:**
  - Client side: `RP:451,464-465` and `area-nav.ts:75-82`.
  - Server side: route `roles`, `mfa: "step_up"` and `canPublishLocation` (`listing-changes.ts:413-415`).
- **Google publish behaviour:** one hash-pinned call per area, the same call each editor makes (`reads.ts:60-65`).

## 7. Friction

- **F1 (P1): the parked or unconfirmed success claims Google accepted everything.** With a two-person-parked step, `publishOutcome` returns `awaiting_approval`, so the title reads "Sent for approval". The description still says "Google accepted every change. Some haven't been read back yet…" (`RP:545-548`), but nothing went to Google (`lib/editors/outcome.ts:47-50`). The tone is `ok` with a `CheckIcon` (`RP:532-533`). This misstates server truth. Evidence: code path `use-publish-flow.ts:254-265` → `RP:539,546-548`.
- **F2 (P2): one unreadable area blocks the whole publish.** `unreadable` ignores `excluded` (`RP:414-422,468-469`), and the include checkbox is drawn only when a review exists (`RP:191`). So the operator can't leave out an area Google failed to read and publish the rest. Hypothesis: this is common when one area's Google read times out.
- **F3 (P2): read-only and requester roles get live controls that do nothing.** For `cannotPublish` the page still shows the include checkboxes (`RP:636-649`, disabled only while publishing), the consent checkbox (`RP:678-685`) and a full docked bar with a disabled primary (`RP:738-782`). Each card's "Edit" (`RP:157-164`) opens a read view. A requester has no next step except asking someone off-app. Evidence: Phase 2 item 1 scenario, `area-nav.ts:75-82`.
- **F4 (P2): a disabled reason is invisible on touch when no step is queued.** The status shows the reason only if `steps.length > 0` (`RP:761`). Otherwise it reads "0 fields will change on Google". The reason lives in a hidden span and the `title` tooltip (`components/ui/button.tsx:251-257,276-277`), and the tooltip can't be seen on a phone. Examples: "Include at least one area to publish." and "Nothing is left to publish." (`RP:472-476`).
- **F5 (P2): focus is lost on success.** When `done`, the bar and button unmount and the result list mounts fresh. A freshly mounted `aria-live` list isn't reliably announced, and focus falls to `<body>`. Failure already moves focus (`RP:488-501`); success doesn't. Hypothesis: a screen-reader user hears only the toast.
- **F6 (P3): the hours-blocked alert has no action.** The copy says "Open the hours editor…" (`reads.ts:153-155`), but the alert has no link (`RP:207-212`). The only route is the small ghost "Edit" in the row header.
- **F7 (P3): two count units in one bar.** The status counts fields ("3 fields will change on Google"), while the button counts areas ("Publish 2 areas to Google") (`RP:759-760,779`). Both are correct, but the mixed units slow scanning.
- **F8 (P3), hypothesis:** a member with a publish grant (`canPublish` true) gets the button. The profile POST, however, is `roles: ["owner","admin"]` (`profile/route.ts:75`), so their profile step would 403 while hours and menu go through. This needs server-team confirmation and is **not a UX-only fix**.

## 8. Proposed changes (all in `RP` unless flagged)

1. **Honest done copy for non-live outcomes (F1).**
   - Change: in `RP:543-548`, use `describeOutcome(publishOutcome(flow.results)).description` whenever the outcome is not `confirmed_applied`, and keep the "Google accepted every change and read it back…" sentence only for confirmed.
   - Change: set `tone` and `icon` by outcome. `ok`/`CheckIcon` stays only for confirmed or all-noop; use a neutral `ClockIcon` for `awaiting_approval`/`sent`/`awaiting_confirmation` (`RP:532-533`).
   - Benefit: no "Google accepted" before the server says so. Principle: Nielsen #1 (visibility of system status), WCAG 2.2 SC 3.3.4 spirit. Shared: no (reads `lib/editors/outcome.ts`, no edit).
2. **Let an unreadable area be left out (F2).**
   - Change: draw the include checkbox when `error` is set too (`RP:191`, condition `include && (review?.rows.length || error)`).
   - Change: filter `unreadable` by `!excluded.includes(area)` (`RP:414`).
   - The excluded area is simply not queued, and consent and hash pinning are untouched.
   - Benefit: publishing doesn't dead-end. Principle: Nielsen #3 (user control), HIG "don't block the task". Shared: no.
3. **A read-only page for roles that can't publish (F3).**
   - Change: when `cannotPublish && !paused`, omit `include`, the ack `AlertActions` checkbox and the `ActionBar`.
   - Change: in `RP:600-601`, set the info alert copy to "Ask an owner or admin to publish these changes." and say "Requests for approval aren't available for listings yet." for `caps.canRequestApproval`.
   - Change: label the row link "View" with aria "View {area}" when `cannotEdit` (`RP:157-164`).
   - Server gates are unchanged.
   - Benefit: no dead controls. Principle: Nielsen #8 (minimalist), WCAG 2.2 SC 3.3.2 (labels or instructions). Shared: no.
   - **Flag:** whether requesters should keep the header link is a `lib/listings/area-nav.ts:75-82` and `area-frame.tsx` (p3) decision, pinned by `tests/listing-area-nav.test.ts:30`.
4. **Always show why Publish is off (F4).**
   - Change: in `RP:761`, show `disabledReason` whenever it is set and no alert already states it, i.e. `disabledReason && !paused && !cannotPublish`, dropping the `steps.length > 0` condition.
   - Change: when `steps.length === 0`, replace "0 fields will change on Google" with the reason alone.
   - Benefit: works on touch. Principle: HIG (explain disabled controls), WCAG 2.2 SC 3.3.2 and 1.3.1. Shared: no (`Button` untouched).
5. **Move focus to the result on success (F5).**
   - Change: add `doneRef` on a `tabIndex={-1}` wrapper around the done block (`RP:522`), then `useEffect(() => { if (done) doneRef.current?.focus() }, [done])`, mirroring `RP:488-501`.
   - Benefit: keyboard and screen-reader users land on the outcome. Principle: WCAG 2.2 SC 2.4.3 (focus order) and SC 4.1.3 (status messages). Shared: no.
6. **An action in the hours-blocked alert (F6).**
   - Change: in `RP:207-212`, add `<AlertActions>` with a secondary `Link` "Open hours editor" to `listingHref(locationId, "hours")`.
   - Optional (F7): reword the bar status to "{n} fields in {k} areas will change on Google".
   - Benefit: recognition over recall. Principle: Nielsen #6, HIG "provide a clear next step". Shared: no.

Not proposed: anything touching `use-publish-flow.ts`, `publish-steps.tsx` or `review-publish-reads.ts` (shared or protected), and F8 (server, roles).
