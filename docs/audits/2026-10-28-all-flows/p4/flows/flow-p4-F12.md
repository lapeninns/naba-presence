## 1. Start and end

- **Start:** the owner or admin opens `/listings/[id]/verification` (`app/(dashboard)/listings/[id]/verification/page.tsx:20-35`, which streams `AreaEditor area="verification"` with `verificationTabPrefetch`). A PIN task exists when Google reports a `pending` request whose method is EMAIL, PHONE_CALL, SMS or ADDRESS (`admin/verification-tab.tsx:46`). The flow can also start from a saved row in "Saved PIN completions" (`admin/verification-saved-workflows.tsx:109-138`).
- **End (success):** a recorded attempt in `OutcomeSummary` ("Accepted by Google", then "Independently confirmed" / "Confirmed on Google" only after an independent read) (`admin/verification-attempt-status.tsx:36-48,140-153`).
- **End (other):** rejected ("Google refused this request"), then "Check Google, then review a corrected PIN" (`admin/verification-completion.tsx:189-199`). Uncertain send, then "Check saved PIN outcome". Drift or expiry, then "Create a fresh PIN review". An unsupported method links to "Continue verification in Google" (`admin/verification-completion.tsx:381-386,397-404`).

## 3. Baseline steps (happy path, one approver, PIN expected)

The PIN section leads the page when `pinExpected` is true (`verification-tab.tsx:76`). Its title is "Enter the PIN from Google" (`:55`).

1. Tap "PIN from Google" and type the PIN. The field is a text input with numeric keypad and one-time-code autofill (`admin/verification-pin-field.tsx:62-75`).
2. Tap **Review PIN completion** (`:57`). A POST preview saves the change set. The PIN is cleared (`:86-92`). Focus moves to the panel heading "Review PIN completion" (`verification-completion.tsx:154-170`).
3. Tap **Approve PIN completion** (`verification-completion-review.tsx:102-108`). MFA step-up may be needed.
4. Tap "Re-enter reviewed PIN" and type the same PIN (`verification-pin-field.tsx:63`).
5. Tick "Submit the reviewed PIN to this exact Google verification request." (`verification-completion-review.tsx:131`, `ConsentSlot`).
6. Tap **Send approved PIN** in the `SendBar` (`verification-pin-field.tsx:57,104-119`).
7. The outcome appears. If it shows "awaiting confirmation", tap **Refresh saved outcome** (`verification-attempt-status.tsx:104-106`).

That is 6 taps plus typing twice, and 7 with the refresh. The 15 Oct audit did not count this task.

**Two people:** the requester stops after tap 2. The approver opens the page and taps "Open saved review" (`verification-saved-workflows.tsx:103`), then Approve. Whoever sends must type the PIN Google delivered to the requester (`lib/server/google-verification-execution.ts:195-196`). The UI never says this.

**Resume:** if the listing is verified at rest, first open the "Verification tools" disclosure (`verification-tab.tsx:81-89`). Then tap "Open saved review" or "Open saved outcome". The work loads into the panel (`verification-completion.tsx:416-439`). An approved review opened from the start workflow needs "Continue approved PIN completion" (`verification-completion-review.tsx:110-118`).

## 5. Protected rules (do not change)

- **PIN never stored or restored.** The client clears it on submit (`verification-pin-field.tsx:89-91`). The server stores only an HMAC commitment under a random encrypted key (`lib/server/google-verification-pin-binding.ts:20-25`). A read never returns it (`lib/server/google-verification-completion-reviews.ts:37`). Execution takes it transiently and checks the commitment, returning `verification_pin_changed` on a mismatch (`google-verification-pin-binding.ts:27-35`; `google-verification-execution.ts:195-196`).
- **Exact revision.** `expectedPayloadHash` is checked on approve and execute (`google-verification-completion-reviews.ts:57`; `google-verification-execution.ts:186,190`).
- **Drift detection.** The baseline hash must match at approve and execute (`google-verification-completion-reviews.ts:49-53`). The request must still be pending (`:19`). Target, connection or credential changes are refused (`:23`; `google-verification-execution.ts:199`). Client codes force a fresh review (`verification-completion.tsx:87-100,250-260`).
- **Team review.** Two-person policy and `canApprove` (`lib/server/gbp-change-sets.ts:50-51`). Approve requires MFA step-up (`…/[reviewId]/route.ts:12`).
- **Idempotency.** There is a per-location lock (`google-verification-execution.ts:183`). An existing attempt returns the durable outcome and is never re-sent (`:184-187`). `startGbpMutation` uses `requestId: reviewId`, `blockUnresolved` and an `unresolvedScope`, and returns early on `claim.idempotent` (`:202-203`). A lost response stays "Send outcome unknown" until a read (`verification-completion.tsx:262`; `verification-saved-workflows.tsx:167`).
- **Audit writes.** `google.verification.completion_requested` (`google-verification-execution.ts:204`), `.completion_rejected` (`:217`) and `.observed` (`:119`).
- **Server authority.** "Confirmed" comes only from an independent read (`google-verification-execution.ts:100-118`). A failed phase never wears the success tone (`verification-attempt-status.tsx:114-135`). Refreshing a recent interrupted request returns `verification_not_ready` for 5 minutes (`google-verification-execution.ts:174`).
- **Unknown methods** cannot take a PIN (`google-verification-completion-reviews.ts:20-21`; `verification-completion.tsx:332-338`).

## 7. Friction

1. **P1: The empty copy can be untrue.** `pending` falls back to `[]` when `current.data` is missing (`verification-completion.tsx:113`; the tab passes `current.data?.verifications ?? []`, `verification-tab.tsx:56`). When the state read fails, the page says "Google has no PIN request waiting for this listing" under the tab's own alert "This does not mean the listing is unverified or has no requests" (`verification-tab.tsx:51`). The two contradict each other on the very fact being asked. Evidence: code.
2. **P2: No hint about where the PIN is.** The field says "PIN from Google" for every method. The hint talks about storage ("cleared after preview…"), not about finding the code in an email, text, call or postcard (`verification-pin-field.tsx:63,77-79`). The method is known at both call sites (`item.method`, `review.payload.method`). Evidence: code.
3. **P2: The review copy is system-speak, and the hand-off is silent.** "Approval binds the PIN entered during preview…" (`verification-completion-review.tsx:49-53`). Nothing tells a second approver, or a requester coming back, that the sender must have the PIN Google delivered. Evidence: code and the flow in `google-verification-execution.ts:195-196`.
4. **P2: Footer hierarchy.** Three secondary or ghost actions show at every stage (`verification-completion-review.tsx:142-156`). "Check saved PIN outcome" means nothing before approval, because no attempt can exist yet (`google-verification-execution.ts:192` requires approval). "Check Google, then review a corrected PIN" does not check Google (`verification-completion.tsx:195`). Evidence: code.
5. **P2: MFA step-up reads as a failure.** Approve and Send return 403 `mfa_step_up_required` (`lib/server/mfa.ts:176`). The prompt opens (`lib/api/client.ts:255-259`), but the panel shows the generic "This action could not finish…" (`use-verification-action.ts:36`). The re-entered PIN has already been cleared (`verification-pin-field.tsx:90`), so the user must type it again and nothing tells them. Evidence: code. Hypothesis: the exact UX of the prompt was not observed.
6. **P3, Hypothesis: a PIN typed before hydration is lost.** The PIN field is server-rendered, and a value typed before React hydrates is reset to `""`. The e2e harness avoids this by waiting (`verification-backend.ts:201-204`). A real user on a slow phone sees the review button stay disabled.
7. **P3: Saved rows don't say who must act.** A two-person review the viewer cannot approve still reads "Awaiting approval" (`verification-saved-workflows.tsx:179`), though `canApprove` and `requiresSecondApprover` are on the item (`lib/contracts/google-verification-workflows.ts:17`). Empty copy: "No current saved PIN completions."
8. **P3: Double alerts on drift.** The panel alert and the mapped `errorNote` both use `role="alert"` (`verification-completion-review.tsx:91`; `verification-completion.tsx:122-126`).
9. **Owner decision, not proposed:** a typo in the re-entered PIN (`verification_pin_changed`) invalidates the review on the client and forces a new review and approval (`verification-completion.tsx:250-259`), even though the server would accept a correct retry. Changing this weakens the deliberate exact-PIN protection, so it is logged as a follow-up only.
