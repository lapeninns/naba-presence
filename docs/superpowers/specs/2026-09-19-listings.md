# Listings — GBP management rebuilt around listing health

Written 2026-09-19. Amends `docs/superpowers/specs/2026-09-18-work-first-ia.md`
§1 (nav) and §3 (location workspace), and §2.2 of the 2026-09-03 agency UX
spec. Identity, tokens and primitives are unchanged.

## Why

Managing a Google Business Profile meant Clients → hub (or All locations for
an unfiled listing) → location → a page that stacked four editors, with two
more segments beside it. Nothing said "listing". Nothing told the operator the
listing's state before they opened every editor, each of which reads Google
live. The save model differed by area. Filing an unfiled listing under a
client took six steps through client settings.

The organising idea: **a listing is a thing with a state.** Linked or not,
verified or not, in sync or changed here or changed on Google, publishing or
failed. The product shows that state cheaply and everywhere, opens the one
area that needs attention, and offers one place to review and publish.

## 1. Navigation

Inbox · **Listings** · Clients · Reports · More (Team, Settings).

Listings is active for `/listings/*`. Clients is active for `/clients/*` only.
The palette's location group is named Listings and links to
`/listings/[id]`. Breadcrumbs read Listings › {Client} › {Listing} › {Area}.

## 2. Routes

| Route                                                                        | Screen                                                                         |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `/listings`                                                                  | The board: every listing the session can see, grouped by client, unfiled first |
| `/listings/[id]`                                                             | Listing overview                                                               |
| `/listings/[id]/profile` · `hours` · `booking` · `photos` · `posts` · `menu` | Focused editors, one per area                                                  |
| `/listings/[id]/people` · `verification`                                     | Owner/admin consoles                                                           |
| `/listings/[id]/suggestions`                                                 | Google's suggested updates                                                     |
| `/listings/[id]/changes`                                                     | Review and publish everything pending                                          |
| `/locations`, `/locations/[id]/*`                                            | Redirect to `/listings/…` (`access` → `people`)                                |

The client hub keeps its location rows; they open the overview.

## 3. The board

One table. Columns: Listing (name, address) · Client · Health · Pending ·
Verification · Last published. Controls: client chips, a health segmented
control (Needs attention · Not linked · Healthy · All), search.

- Unfiled listings sit first, each with an inline **File under…** select
  that calls the existing `POST /api/clients/[id]/locations`.
- Owner/admin action: **Add listings from Google** → `/setup?client=…&step=locations`;
  a client picker first when the board is not filtered to one.
- Members see their listings with linked/verified only; the Pending column
  is blank for them (the summary route answers only what they may see).

## 4. Listing health

`listingHealth()` in `lib/listings/health.ts`, derived and never stored:

| Health                 | When                                                                         |
| ---------------------- | ---------------------------------------------------------------------------- |
| `not_linked`           | No active Google link                                                        |
| `disconnected`         | The link's connection is not active or needs reconnecting                    |
| `pending_verification` | Linked but Google has not verified the listing                               |
| `attention`            | A failed publish in the last attempt, a conflict, or a Google change waiting |
| `unpublished`          | Local edits not yet on Google                                                |
| `healthy`              | None of the above                                                            |

Tones map onto the existing status vocabulary; no new tone.

## 5. Listing summary (the one new endpoint)

`GET /api/locations/[id]/summary` and `GET /api/listings/summary` (all
visible listings, one pass). DB-only; never calls Google. Per area:

- **Profile, hours, menu**: local edits vs. the last published baseline are
  exact ("Not on Google yet"). Google-side changes are as of the last
  observation, with its timestamp ("Changed on Google · checked 2h ago").
- **Booking, photos, people**: write Google directly; counts from the cached
  snapshots.
- **Posts**: drafts, awaiting approval, failed.
- **Suggestions**: pending proposals per resource.
- **Last publish**: newest attempt across every area, with its status.
- **Connection**: status, reconnect needed, login email.

## 6. The overview

Header: client eyebrow, name, address, health pill, sibling switcher,
actions: **Review & publish (n)** when anything is pending, Activity, Open on
Google.

Health strip, four tiles: Connection · Verification · Sync · Last published.

Area cards: Profile · Hours · Booking · Photos · Posts · Menu · People.
Each: status pill from the summary, one line of substance, Edit. Blocked or
unavailable areas say why, from capabilities. A Google-suggestions card
appears when proposals are pending. Recent activity lists the last five
attempts.

The overview paints from the directory, capabilities, the summary,
import-review counts and one activity page. No Google call.

## 7. Focused editors

The existing editors, one per route, under an area header: back to the
listing, the area name, the same status pill as its card, the area's gate.
Google-direct areas carry an info banner: "Changes here go to Google straight
away." Posts keeps its lifecycle. The one-scroll Listing page and the
Listing/Content/Access switcher are retired.

## 8. Review & publish

Lists every area with local edits not on Google, loads each area's diff on
demand (this is where Google is read, at review time), and publishes them in
sequence through the existing publish routes with per-step results.
Conflicts require the same acknowledgement the review sheet already
enforces.

## 9. Onboarding

Same wizard, same steps. After linking, the operator lands on the board
filtered to that client with a backfill note. Verification and reconnect are
visible on the overview from the first visit.

## 10. States

| Surface          | State                 | Shows                                                               |
| ---------------- | --------------------- | ------------------------------------------------------------------- |
| Board            | no listings           | "No listings yet" with Add listings (owner/admin)                   |
| Board            | member                | linked/verified only, no Pending column                             |
| Board row        | unfiled               | File under… select                                                  |
| Overview         | summary failed        | Cards fall back to "Open to check" with the area's capability state |
| Overview         | not linked            | Health strip says so; cards disabled with the link reason           |
| Area card        | unavailable / blocked | Capability reason in the card body, no Edit                         |
| Review & publish | nothing pending       | Not offered                                                         |
| Review & publish | a step fails          | Per-step result, later steps not run, cards refresh                 |
