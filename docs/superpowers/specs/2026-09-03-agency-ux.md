# NabaPresence agency UX — specification

Written 2026-09-03. This is the UX blueprint for the second frontend rebuild.
It replaces the single-venue information architecture shipped in August 2026
with one designed for an agency that manages Google Business Profiles (GBP)
for many client businesses. It is the reference for the mockup canvas and for
every Phase B milestone; where a screen and this document disagree, this
document wins until it is amended.

Decisions recorded here were made by the product owner on 2026-09-03:

| Decision | Answer |
|---|---|
| Scope | Everything, including visual identity |
| Primary persona | Agency managing many clients' listings |
| Tenancy | Agency = one organisation. New **Client** entity above Location inside the org. No cross-org portfolio; org switching stays a minor account-menu item |
| Visual direction | Calm, editorial, light-first |
| Mobile | Companion: triage, approve, alerts, read-only client overview |
| Deliverable order | This spec plus mockups first, then build |

Related documents: `docs/frontend-backend-feature-map.md` (surface inventory
and backend readiness, still accurate), `docs/architecture.md` (server
patterns), `docs/superpowers/specs/2026-07-31-frontend-rebuild-design.md`
(the previous blueprint; its §7 token policy and §8 auth contract are
superseded by §6 and §4.4 here).

## 1. Personas and jobs

**Agency account manager (primary).** Looks after eight to forty client
listings. Opens the product several times a day to clear reviews that need a
reply, approve AI drafts a colleague has prepared, and check that nothing is
broken. Works on a laptop; checks and approves on a phone between meetings.

**Agency admin (owner/admin role).** Onboards new clients, connects Google
logins, links locations, invites staff and decides who may publish. Cares
about setup progress and about which client's Google connection has failed.

**Client-side viewer (viewer role, occasional).** A business owner given
read access to their own client. Wants to see reviews, replies and
performance for their locations and nothing else.

Jobs, in priority order:

1. Clear the reply backlog across every client without losing track of which
   business a review belongs to.
2. Approve or reject a drafted reply with confidence that it was verified.
3. Onboard a new client from zero to "reviews flowing" in one sitting.
4. Keep every client's profile, hours, photos, posts and menus correct on
   Google, with a visible diff before anything is written.
5. Notice, and fix, a broken Google connection before the client does.
6. Report per client.

The four pain areas the owner named, as problem statements:

- **Onboarding and connection.** Setup is a stack of cards on a settings page
  with no order, no progress and no notion of "which client is this for".
- **Inbox and approval.** The list pages seven rows at a time over a partial
  window; the reply lifecycle is implied rather than shown; there is no
  keyboard flow and no bulk action.
- **Editors.** Two parallel navigations render the same editors; save and
  publish behave differently on every tab; Industry is a JSON console.
- **Navigation and mobile.** Sidebar labels disagree with URLs, there are no
  breadcrumbs, no account or org menu, and the phone layout is the desktop
  layout squeezed.

## 2. Information architecture

### 2.1 Primary navigation

Six org-wide items in three visual groups. Group labels are plain `<span>`s
referenced by `aria-labelledby` on each `<ul>`, never headings, so the pinned
axe rules (`heading-order`, `page-has-heading-one`) are unaffected.

| Group | Item | Route | Purpose |
|---|---|---|---|
| Work | Home | `/home` | Today: setup checklist, work by client, clients needing attention, review pulse |
| Work | Inbox | `/inbox` | Every review across every client; filter by client and locations |
| Clients | Clients | `/clients` | The hub. Up to six pinned or recent clients appear beneath it with a health dot |
| Org | Reports | `/reports` | Performance by client, drill to location |
| Org | Team | `/team` | Members, roles, client assignments, invitations |
| Org | Settings | `/settings` | Reply policy, compliance, Google connections, operations |

`Clients` is the active item for `/clients/*` and `/locations/*`.

### 2.2 Client hub and location workspace

`/clients/[clientId]` is the hub for a client. The per-location workspace
stays at `/locations/[id]/*` because it owns the real editor code, prefetch
and end-to-end coverage; it gains a breadcrumb `Clients › {Client} ›
{Location} › {Section}` and a location switcher scoped to the client's
sibling locations.

| Route | Content |
|---|---|
| `/clients` | Table of clients: name, health, linked/total locations, open work, last sync. "Unassigned locations" group when any location has no client. "New client" (owner/admin) |
| `/clients/new` | Name, colour, notes; on save hands off to `/setup?client=<id>&step=connect` |
| `/clients/[clientId]` | Header (name, health chip, the Google login behind it, Reconnect when needed); work queue for this client; locations with linked / verified / backfill state and quick links into each section; recent activity |
| `/clients/[clientId]/settings` | Rename, colour, notes, archive; assign or unassign locations; "Add locations from Google" re-enters the wizard |
| `/locations/[id]/*` | Location workspace, sections below |
| `/locations` | Org-wide "All locations" table grouped by client; reached from the Clients header and the command palette, not from the sidebar |
| `/setup` | Onboarding wizard (§4.1) |
| `/team`, `/reports` | Promoted from `/settings/team` and `/performance` |

Location sections (tabs inside the workspace):

| Section | Segments |
|---|---|
| Overview | `` (summary: health, pending changes, suggested updates count, recent activity) |
| Profile | `profile` (Business profile, merged), `hours`, `suggestions` (Google-suggested updates) |
| Content | `photos`, `posts`, `menu` |
| Customers | `booking` |
| Access | `access` (people, invitations, danger zone), `verification` |
| Insights | `performance` |

`business-information`, `industry` and `administration` become redirects into
`profile` and `access`.

### 2.3 Redirects (retiring the flat single-business routes)

| From | To |
|---|---|
| `/profile`, `/profile/hours`, `/profile/menu`, `/profile/booking`, `/profile/details`, `/profile/industry`, `/photos`, `/posts` | `/locations/[primary]/<segment>` when exactly one location is visible to the user, otherwise `/clients` |
| `/performance`, `/analytics` | `/reports` (query forwarded) |
| `/settings/team` | `/team` |
| `/settings/listing` | `/locations/[primary]/access`, otherwise `/clients` |
| `/overview`, `/reviews`, `/login`, `/connections` | unchanged targets |

### 2.4 App shell

- **Sidebar**: brand mark with the agency name, grouped navigation, account
  menu trigger at the foot.
- **Topbar**: mobile navigation trigger, breadcrumbs (`<nav
  aria-label="Breadcrumb">`, populated by layouts through a context), a
  "Search ⌘K" button, a context health chip, theme toggle, account menu.
- **Command palette** (⌘K, or `/` when focus is not in a field): groups
  Clients, Locations, Go to (Home, Inbox, Reports, Team, Settings), Actions
  (New client, Connect Google, Invite teammate). Inside the inbox it also
  offers actions on the selected review.
- **Account menu**: name, email, role badge; "Switch organisation" only when
  the user belongs to more than one; Sign out.
- **Context health chip**: inside a client or location, that client's health;
  on org-wide pages, the aggregate ("All clients connected" or "2 clients need
  attention", linking to Home's attention list). Changes are announced through
  a polite live region, first paint stays silent.
- **Reconnect banner**: shown only inside the affected client's pages, names
  the client and the Google login, offers one Reconnect action. Org-wide pages
  carry the problem in Home's attention list instead of a global red bar.

### 2.5 Mobile companion

Same routes, no separate IA. The sidebar becomes a sheet. Inbox is list-first
with a pushed detail pane; the queues rail and filters open as sheets. The
client hub renders its read-only overview. Editors remain reachable and
responsive but are not optimised for a phone.

## 3. Client model

- **Entity**: `client` (id, organisation, name, slug, colour, logo, notes,
  archived) with `location.client_id` nullable. Unassigned locations are shown
  as a group, never as a fake client.
- **Backfill**: one client per Google account that has linked locations,
  named after the account; locations follow their link.
- **Health** (derived, never stored): `not_connected` (no linked locations),
  `disconnected` (every connection inactive or reconnect required),
  `attention` (some inactive, a failed or dead backfill, or no successful
  refresh in 24h), `syncing` (backfill running), `healthy`.
- **Visibility**: a client is visible when at least one of its locations is
  visible under the existing single rule in `lib/server/permissions.ts`.
  Owners and admins see everything. Members and viewers are scoped through
  per-location grants; the Team page writes those grants per client so the
  operator never thinks in locations unless they want to.
- **Filters**: `clientId` becomes a first-class filter on reviews, review
  counts, analytics overview, presence, keywords and Home work queues.
  Reviews also accept `locationIds[]`.

## 4. Flows

### 4.1 Onboarding wizard

Entered automatically by an owner or admin who has no client and no location,
from "New client", or from a client's "Add locations from Google". The step
shown is derived from the client's actual state, so refresh, back and resume
all work without stored progress.

| # | Step | What the user does | Reuses |
|---|---|---|---|
| 1 | Agency | Confirm agency name and default timezone | `PATCH /api/settings` |
| 2 | Client | Name the first client, pick a colour | `POST /api/clients` |
| 3 | Connect | "Connect the Google account that manages this client's Business Profile", or "Use an already-connected Google account" | `POST /api/google/connect/start` with `clientId` and `returnTo` |
| 4 | Account | Tick the GBP account(s) behind this client; copy explains one Google login can manage many GBP accounts | `GET/PATCH /api/google/accounts` |
| 5 | Locations | Multi-select discovered locations; relink conflicts confirmed per row | `GET /api/google/locations`, `POST /api/location-links` |
| 6 | Backfill | Watch progress per location; "Continue while it runs" | `POST/GET /api/sync/backfill` |
| 7 | Notifications | Enable real-time review notifications per account (optional) | `PATCH /api/google/notifications` |
| 8 | Team | Invite colleagues, optionally scoped to this client (optional) | `POST /api/invitations` |
| 9 | Done | Land on the client hub | — |

A "Setup" card on Home shows the same checklist for the first client until it
is complete or dismissed.

### 4.2 Add another client

`/clients/new` → wizard at step 3 with "Use an already-connected Google
account" pre-selected when any active login exists → steps 4 to 9.

### 4.3 Reconnect

From the client hub header, a client-scoped banner, or Settings › Connections.
Same-login re-consent silently restores. A different login creates a new
connection and the hub offers "Move to new login", which re-runs discovery and
relinks with confirmation.

### 4.4 Invitation and sign-in

Sign-in and create-account share one split-screen page with a segmented
toggle; copy changes with the mode ("Welcome back / Sign in to run your
clients' reviews" and "New agency / Create your agency workspace"). Invitation
pages use the same panel with eyebrow "Invitation", title "Join {agency}",
and a line stating the role and who invited them; a signed-in visitor whose
email matches can accept in place. Forgot and reset pages gain the eyebrow
"Account recovery". After sign-in the user lands on `?next=` or `/home`.

### 4.5 Review triage → approve → publish

1. Open Inbox. The rail shows queues grouped by client with counts: Needs
   reply, Awaiting my approval, Awaiting others, Publishing, Failed, Done.
2. Pick a queue or a saved view; the list loads continuously.
3. `j`/`k` move, `x` selects, `r` focuses the reply, `a` approves, `e`
   assigns, `?` lists shortcuts.
4. The detail pane shows a lifecycle strip Received → Drafted → Verified →
   Approved → Published with who and when. Verification findings sit beside
   the draft as annotations; "Show in reply" highlights the offending span.
5. Approve, or edit and re-verify, then publish. Two-person approval shows
   "A different authorised user must approve this reply" to the requester.
6. A failed publish shows a banner with the humanised cause, Retry and
   "Edit reply".
7. Bulk: select rows → "Approve (3 of 5 eligible)", "Assign", "Mark
   reviewed" → per-row result summary.

### 4.6 Editor draft → review changes → publish

Every Google-writing editor uses one model: edit locally → status pill turns
"Edited" → "Review changes" opens a sheet with the field-level diff and any
overwrite acknowledgement → "Publish to Google" (or "Save draft only" for
resources that keep a canonical copy). Activity is a drawer opened on demand.

### 4.7 Suggested updates

Google's proposed changes render as field rows with before and after, each
with Accept or Ignore; a summary shows how many are pending; decisions apply
in sequence with a per-row result.

## 5. Screen inventory and states

Every screen must handle: loading, empty, disconnected, read-only,
permission-denied, unsupported, stale, partial failure, success, retry.

| Screen | Key content | Notable states |
|---|---|---|
| Sign in / Create agency | Split screen: marketing rail with three beats ("Every client's reviews in one inbox", "Approve replies before they go live", "Publish to each client's Business Profile"); form panel | Unconfirmed email → "Check your email" with resend; invitation expired → dead end with exit |
| Setup wizard | Stepper (`<ol aria-current="step">`), one step body, Back / Continue | Connect error mapped to plain copy; backfill failed per location with Retry; resume at next incomplete step |
| Home | Setup card (until done), work by client (top N by open work), attention list (unhealthy clients first, then low-rated locations), pulse chart, KPI tiles | No clients → "Set up your first client" (owner/admin) or "Your agency hasn't set up any clients yet" |
| Clients index | Data table with health pill, counts, open work, last sync; Unassigned group | Empty; member sees only their clients |
| Client hub | Header with health and Reconnect; work queue; locations; activity | Disconnected banner scoped here; no locations → "Add locations from Google" |
| Client settings | Form; assign locations table; archive | Archive blocked while locations attached |
| Inbox | Rail · list · detail (resizable); filter chips; bulk bar | Filtered-empty with Clear; client-disconnected; client-no-locations; stale list bar |
| Review detail | Lifecycle strip; review; draft with annotations; action bar | Publish failed banner; two-person notice; read-only for viewers; delete-reply confirm |
| Business profile editor | Sections: identity, categories, contact, address & service areas, attributes, description, plus lodging / calls / healthcare when eligible | Capability banner (read-only, blocked, unavailable); conflict acknowledgement in sheet |
| Hours editor | Weekly grid, copy-to-days, special hours calendar | Timezone line; validation before publish |
| Photos | Gallery, upload with progress, cover/logo | Upload validation before request |
| Posts | List, composer sheet with live preview, schedule | Reconciliation error inline |
| Menu, Booking | Nested editor; link preview with preferred toggle | Unsupported when not eligible |
| Suggested updates | Field rows with accept/ignore; summary | None pending |
| Access, Verification | People table with role badges; method cards, PIN, history | Owner-only actions gated with visible reason |
| Reports | Client selector; by-client table expanding to locations; charts | Metrics unavailable reasons listed |
| Team | Members grouped by client assignment; invite dialog | Last-owner rule |
| Settings › Connections | Connections table with the clients each login serves; reconnect, disconnect (with purge acknowledgement) | Reconnect required per row |
| Access denied | "You don't have access to this page", who to ask, Back to Home | Replaces every silent redirect |
| Not found | Inside the shell, "Back to Clients" | — |

## 6. Visual identity

Direction: calm, editorial, light-first. Paper-like warm neutrals, generous
type, one restrained accent, borders rather than shadows, dark mode as a
faithful inversion.

- **Neutrals**: one warm hue (oklch hue 70–85, chroma 0.003–0.012). Light:
  canvas ≈ 0.985, surface 1.0, sunken ≈ 0.96, ink ≈ 0.25, muted ink ≈ 0.50.
  Dark inverts on the same hue with a touch more chroma.
- **Accent**: one hue, chroma 0.08–0.12, dark enough to carry white text at
  4.5:1. Illustrative: deep teal `oklch(0.46 0.10 200)`. Roles: solid, hover,
  active, tint, ink, ink-on-accent.
- **Status**: success ≈ 150, warning ≈ 72 (ink kept dark), danger ≈ 27, info
  ≈ 240; each with ink, tint, solid, on-solid, line. Health tones: healthy,
  attention, at-risk, pending, neutral.
- **Type** (closed set): caption 12/16 · ui 13/20 · body 14/22 · title 16/24
  · section 18/26 · page-title 26/32 · display 32/38. Geist Sans for UI and
  body; one serif display face (loaded through `next/font` with a Georgia
  fallback) for page titles and display numbers; Geist Mono unchanged.
- **Shape**: radius tag 4, control 8, field 8, card 12, panel 12, modal 16,
  pill 999. Border-led elevation with three line tokens; shadows only on
  popovers, modals, toasts and a single raised-hover step. Focus ring 2px
  accent with 2px offset.
- **Density**: comfortable by default; compact by default for data tables
  and the inbox list; a persisted user toggle. Compact controls never fall
  below 24px.
- **Tokens**: a new `--np-` namespace in four layers (ramps → semantic roles
  → component tokens → compatibility aliases for the shadcn contract and the
  old `--nr-*` names). A contrast validator (`pnpm check:contrast`, also run
  under vitest) checks every foreground/background pair in both themes and
  refuses `color-mix` in checked roles.

## 7. Accessibility and content rules

- One `<main>` per page, owned by the page frame. Panes are labelled
  `section` or `nav` elements. Heading order is h1 (page) → h2 (pane or
  section) → h3.
- Every disabled control carries visible reason text, never a tooltip alone.
- Keyboard shortcuts never fire inside editable fields except ⌘K.
- Copy never names environment flags, provider error codes or internal
  vocabulary; `lib/errors/action-errors.ts` remains the one map from code to
  sentence.
- Both colour schemes pass WCAG AA; every page loads with zero console
  errors.

## 8. Out of scope

Cross-organisation portfolio views, bulk edits across many locations,
white-label branding, persisted saved inbox views (URL presets ship first),
and support impersonation UI.
