# Redesign 2026-11 — Inventory (coverage contract)

Base `367719b3`. Owner: worker `a-inventory`. This file is the mission's coverage contract. Every route file under `app/` and every user-facing surface without its own route has one row `Rnn`, and `MISSION.md`'s coverage table is keyed by these ids. `node docs/redesign/2026-11/check-inventory.mjs` proves completeness: it fails on any `app/` route file missing from the "Route files" column, any `app/api` group missing from §3, or row ids that repeat or skip. Run it with `--manifest <capture>/manifest.json` and it also checks that every `page` row's capture shots exist at phone, tablet and desktop.

**How rows were made.** Each route group was read by a separate code reader, and a completeness critic then swept `components/` and `app/` for surfaces with no row. Paths and file names were checked to exist. A file appearing in two rows was treated as an error, and none remain. Then an adversarial pass gave all 164 rows to six skeptics, each told to refute roles, data, states, components and mode against the code. It made **41 corrections**: 7 roles, 7 mode, 6 data, 18 states, 3 notes/verified. The most common correction was share-report surfaces wrongly marked agency-only; business workspaces share their home client from Reports. Each correction is logged with its file:line evidence in the a-inventory evidence (`corrections.log`). **No row was verified by rendering** (BASELINE §2: the sandbox cannot bind ports). The "Verified by" column says which code proves each state. State cells therefore mean:
- **present:** the code renders this state;
- **absent:** the code has no such state where one could apply;
- **unknown:** not determinable from the code.

State vocabulary: loading, empty, filtered-empty, partial, stale, offline, validation, permission, read-only, pending, success, recovery.

**Columns.**
- **Kind:** `page`, `layout`, `loading`, `error`, `not-found`, `global-error`, `handler` (user-facing `route.ts`), `redirect` (a page that only redirects) or `surface` (a dialog, sheet, drawer, bar, panel or menu with no route).
- **Capture:** the nm-capture shot names (`tests/visual/nm-capture-lib.mjs` `DEFAULT_ROUTES` + the `STATES` in `nm-capture.mjs`), filled in for page, redirect and handler rows. Before-evidence lives at `<evidence>/a-inventory/before-367719b3/{phone,tablet,desktop,desktop-dark,phone-dark}/<shot>.png` once `tests/visual/nm-capture-before.sh` has run.
- **Roles:** owner, admin, member (assigned or unassigned), viewer, requester or approver (approval org), anon. The model is in BASELINE §3.4.
- **Mode:** business, agency or both (BASELINE §3.3).

### auth

The file is valid JSON with 8 route rows and 4 surface rows (MFA step-up prompt, password requirements, resend confirmation, invitation actions). Every file path cited in it exists. All findings come from reading code; nothing was rendered.

1. The brief asked whether password sign-in is disabled. It is not. Sign-in is email + password through Supabase Auth (lib/server/password-auth.ts), behind PASSWORD_AUTH_ENABLED, which defaults to true. When that flag is off, the login and register routes return 503 password_auth_disabled. There is no magic-link sign-in. The emailed links only confirm an email address or start a password reset, and they go through app/auth/confirm/route.ts, where GET never uses up the one-time token and only the POST from /confirm-email does. Google OAuth (app/api/auth/callback/google/route.ts) connects a Business Profile to an existing session; it is not a way to sign in to the app.

2. LOCAL_BOOTSTRAP: auth pages never create a local session. When NODE_ENV is not production, or LOCAL_BOOTSTRAP_ENABLED is set and NEXTAUTH_URL is localhost, both app/page.tsx and app/(dashboard)/layout.tsx skip sign-in. AppShell then calls GET /api/session, which runs ensureDevelopmentSession and creates a local owner session. So in local dev /sign-in is only reached by typing the URL. lib/server/startup.ts rejects LOCAL_BOOTSTRAP_ENABLED on any non-localhost deployment.

3. The sign-in page reads a ?invite= parameter, but nothing in the repo builds a /sign-in?invite= link. Invitation emails go to /invite/[token]. That code path may be legacy or used only by outside links.

4. MFA_ENABLED defaults to off. With it off, /sign-in/verify just redirects to /sign-in and the step-up prompt never appears. When it is on, the prompt shows only to owners and admins. 55 route files declare mfa: "step_up", and 3 more call requireRecentMfa directly. The surface row lists a representative subset, not all 55.

5. The (auth) group has no loading.tsx and no not-found.tsx, and only /invite/[token] mounts a QueryProvider.

6. None of the auth screens shows a separate offline state; network errors go through the generic authErrorMessage. I marked offline as absent everywhere. I did not trace the exact wording shown for a network_error.
